# Практика 11. Обработчик файлов заказов

В конце смены служба поддержки получает несколько файлов с заказами. Нужно узнать, сколько строк и слов в каждом файле. Код, который считает строки и слова в одном файле, уже готов. Ваша задача — распределить файлы между несколькими горутинами и собрать ответы.

## С чего начать

Откройте папку с этим README в IDE. Команды запускайте в терминале из той же папки, где лежит `go.mod`. Подойдёт Go 1.22 или новее.

```bash
go run ./cmd/filecount
go test -run '^TestAnalyzeFile$' ./processor
go test -timeout 15s ./processor
```

Программа пока пишет `Обработано файлов: 0`. Первый тест проверяет подсчёт в одном файле и проходит. Когда вы запустите все тесты, `TestProcessFiles` сообщит, для каких файлов он ждал ответ. Этим вы и займётесь в функции `ProcessFiles`. [Заготовка](processor/processor.go)

## Что должна делать функция

`ProcessFiles(paths []string, workers int) <-chan Result` получает список путей и число работников. Работник — это горутина, которая берёт из канала `jobs` путь к файлу, обрабатывает его и берёт следующий. Например, три работника могут разобрать двадцать файлов. Если передано `workers < 1`, заготовка уже выбирает одного работника.

Для каждого пути работник вызывает готовую функцию `analyzeFile` и отправляет её результат в общий канал `results`. В результате есть путь (`Path`), число строк (`Lines`), число слов (`Words`) и ошибка (`Err`). [Подсчёт в одном файле](processor/file.go)

При проверке обратите внимание на три случая.

- Если один путь встретился в списке дважды, получите по нему два ответа.
- Если файл не удалось открыть, верните ответ с его путём и ошибкой. Продолжайте обрабатывать остальные файлы.
- Если список пуст, цикл `range` по результатам должен закончиться, не получив ни одного значения. Для непустого списка допустим любой порядок ответов.

## 30 минут в классе

**0–8 минут. Запустите работников.** Откройте `testdata/orders-a.txt` и пересчитайте строки и слова. Сверьте с таблицей ниже. Затем откройте `ProcessFiles`. Для первого опыта создайте канал `jobs` и сразу закройте его. Запустите `workers` горутин. Каждая читает `jobs` через `range`, а когда цикл закончится, печатает «работник завершился». Используйте `sync.WaitGroup`, чтобы дождаться всех работников перед выходом из функции.

К восьмой минуте запустите `go run ./cmd/filecount`. Вы должны увидеть три сообщения от работников, а за ними — итог `Обработано файлов: 0`. На этом шаге вы ещё не раздавали файлы.

**8–20 минут. Раздайте файлы и соберите ответы.** Уберите пробную печать. Передайте через `jobs` все пути и решите, когда его закрыть. Работник получает путь, вызывает `analyzeFile` и отправляет ответ в `results`. Кто узнает, что все ответы отправлены и пора закрыть `results`? Функция `main` должна получить канал вовремя, чтобы читать ответы, пока работники их отправляют.

На четырнадцатой минуте покажите в коде, где путь к первому файлу отправляют в `jobs` и где его получает работник. К двадцатой минуте запустите `go test -timeout 15s ./processor` и `go run ./cmd/filecount`. Теперь в выводе должны быть три файла.

**20–30 минут. Проверьте решение.** Сверьте числа для каждого файла с таблицей. Добавьте свой тест. Например, передайте два пути, один к существующему файлу, другой — к отсутствующему. Затем выполните команды проверки из раздела «Домашнее задание». К концу занятия покажите, как ваша программа узнаёт, что получила последний ответ.

## Какие числа должны получиться

| Файл из `testdata/` | Что в нём особенного | Строк | Слов |
|---|---|---:|---:|
| `orders-a.txt` | Между двумя заказами есть пустая строка | 3 | 5 |
| `orders-b.txt` | Есть табуляция, в конце последней строки нет перевода строки | 2 | 4 |
| `empty.txt` | Файл пуст | 0 | 0 |

Внутренняя пустая строка тоже считается. Последняя строка может закончиться вместе с файлом. Если после последней записи стоит перевод строки, он завершает эту запись. Слова могут разделяться пробелами и табуляцией.

При обычном запуске после статистики по этим файлам программа напечатает `Обработано файлов: 3`. Можно также передать программе только два нужных пути.

```bash
go run ./cmd/filecount testdata/orders-b.txt testdata/orders-a.txt
```

## Домашнее задание

К следующему занятию закончите этот же обработчик. Проверьте, что несколько работников получают пути из `jobs`, возвращают ответы через `results` и что программа ждёт их завершения с помощью `sync.WaitGroup`. Выполните обе команды в корне проекта.

```bash
go test -race -timeout 15s -coverprofile=coverage.out ./...
go tool cover -func=coverage.out
```

Все тесты должны пройти, а в отчёте детектора не должно быть предупреждений о гонке. Детектор видит только обращения к памяти, которые произошли во время запуска тестов. Последняя команда покажет покрытие — долю операторов программы, выполненных тестами. Требование к работе — не менее 60% в строке `total`.

**Если осталось время.** Добавьте общие для всех работников счётчики строк и слов. Когда работник успешно прочитал файл, пусть прибавит его строки и слова к общим. Как защитить такое обновление одним `sync.Mutex`? Проверьте обе суммы по трём файлам из таблицы.

## Вопросы к следующему занятию

1. Как Go запускает много горутин на нескольких потоках ОС? Что может делать другая горутина, пока первая ждёт ответ по сети?
2. Горутина отправляет номер заказа в открытый канал без буфера. Кого она ждёт? Что изменится, если в буфере есть два свободных места?
3. Кто в вашем обработчике знает, что путей больше не будет и пора закрывать `jobs`? Кто может закрыть `results`? Что случится, если работник отправит ответ в закрытый канал?
4. Два работника прибавляют по единице к общему счётчику. Как одно прибавление может потеряться? Можно ли по одному правильному итогу понять, есть ли гонка? Как здесь помогает `Mutex`?
5. Кухня и витрина читают статус заказа, а оператор меняет его на «готов». Кто может использовать `RLock`, а кому нужен `Lock`? Как проверить, даёт ли `RWMutex` выигрыш в скорости?
6. Функция взяла замок и вышла с ошибкой, забыв его освободить. Что будет со следующим работником? В каком месте поможет `defer Unlock()`? Что произойдёт, если одна горутина попробует взять тот же замок дважды подряд?
7. Проследите конец работы вашей программы. Когда закрывается `jobs`? Когда приходит последний ответ? В какой момент все работники уже закончили, `Wait` вернул управление и завершился `range` по результатам? Какие из этих событий могут поменяться местами?
