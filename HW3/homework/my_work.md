# Сервис уведомлений

## Что делает программа

Программа имитирует рассылку уведомлений через email и push. Каждый канал
сохраняет успешно отправленные сообщения в своей истории с префиксом `[email]`
или `[push]`. Реальная отправка по сети не выполняется; адрес и устройства учебные.

## Как запустить

Нужен Go 1.22 или новее со стандартным поведением `panic(nil)`.
Корень Go-модуля `lesson5/student` в этом репозитории — папка `HW3`
(в условии она называется `student`). Из корня репозитория выполните:

```bash
cd HW3
go run ./cmd/notify
```

Одна команда запускает все четыре сценария. Из той же папки выполняются проверки:

```bash
gofmt -w practice/tasks.go cmd/notify/main.go
go test -v ./practice -run TestHomework
go test ./...
go build ./...
go vet ./...
gofmt -l practice/tasks.go cmd/notify/main.go
```

Последняя команда не должна ничего выводить. Чтобы отдельно проверить шаги
практики, можно выполнить `go test -v ./practice -run TestStep`.

Если в WSL команда `go` не найдена, а Go установлен в `/usr/local/go`,
добавьте его в путь для текущего терминала: `export PATH=/usr/local/go/bin:$PATH`.
Решение проверено на Go 1.27.1 в WSL: все тесты, сборка и `go vet` проходят,
`gofmt -l` ничего не выводит, все четыре сценария запускаются.

## Проверенные случаи

1. **Успех.** `Dispatch` отправляет `Заказ готов` в email с адресом
   `student@example.com` и push с `DeviceID: "phone-1"`, возвращая `nil`.
   Истории содержат `[email] Заказ готов` и `[push] Заказ готов`.
2. **Пустой текст.** Повторный вызов `Dispatch` с `""` возвращает обёрнутую
   `ErrEmptyMessage`, которую распознаёт `errors.Is`. Обе истории остаются
   прежними: по одному сообщению из первого сценария.
3. **Нет настройки.** Push с пустым `DeviceID` не сохраняет `Заказ готов`.
   `errors.As` извлекает `*SendError` с `Channel: "push"` и
   `Reason: "не задан device id"`. Его история остаётся пустой.
4. **Паника одного канала.** В `SafeDispatch` первым идёт `BrokenNotifier`,
   вторым — исправный push с `DeviceID: "phone-2"`. Возвращается одна ошибка,
   распознаваемая через `errors.Is(err, practice.ErrNotifierPanic)`, с текстом
   паники `драйвер канала повреждён`. Следующий push получает `Заказ готов`
   и сохраняет `[push] Заказ готов`.

## Обработка ошибок

`ErrEmptyMessage` — одна общая ошибка, созданная через `errors.New`.
Оба канала сначала проверяют пустой текст, затем свою настройку. Поэтому при
одновременно пустых сообщении и настройке возвращается `ErrEmptyMessage`.
У email отсутствие адреса даёт `*SendError` с причиной `не задан адрес`,
у push отсутствие устройства — с причиной `не задан device id`.
Любая из этих ошибок оставляет прежнюю историю без изменений. Строка `" "`
допустима: пробелы не обрезаются.

`Dispatch` последовательно вызывает `Send` и останавливается на первой ошибке.
Он добавляет имя канала через `fmt.Errorf("канал %s: %w", ...)`, сохраняя
исходную причину. Паники этот диспетчер не перехватывает.

`SafeDispatch` вызывает `SafeSend` для каждого канала, продолжает после обычной
ошибки или паники и возвращает слайс всех ошибок в порядке каналов. Каждая ошибка
тоже получает контекст через `%w`. Оба диспетчера возвращают успешный результат
для пустого списка каналов.

В `SafeSend` отложенная функция напрямую вызывает `recover`. При панике она
присваивает именованному результату ошибку с `ErrNotifierPanic` через `%w`
и значением паники через `%v`. Обычный результат `Send` возвращается без замены.
Перехват расположен вокруг отдельного `Send`, чтобы после возврата из
`SafeSend` цикл `SafeDispatch` мог вызвать следующий канал.

В `cmd/notify/main.go` `errors.Is` определяет пустой текст и панику канала,
а `errors.As` извлекает ошибку настройки. Поля `SendError` читаются только после
успешного `errors.As`. Выбор поведения не зависит от текста ошибки: `%w`
сохраняет цепочку для проверок. Самому `SendError` метод `Unwrap` не нужен.
Все сообщения об ошибках выводятся в `main`; каналы и диспетчеры не печатают их.
